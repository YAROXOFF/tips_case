\# Роли и права — кейс 3



\## Как заполнять

Даны 2 роли из 4. Заполни «официант» и «администратор», затем опиши

процесс регистрации мерчанта и сотрудника.



\## Матрица ролей (заполни)


| Действие | Мерчант | Официант | Клиент | Администратор |
|—|—|—|—|—|
| Регистрация в платформе | да | да (по приглашению мерчанта) | нет (анонимен) | да |
| Генерация QR на чек | да | да | нет | нет |
| Просмотр своих чаевых | да | да (только свои) | нет | да |
| Сканирование QR | нет | нет | да | нет |
| Оплата чаевых | нет | нет | да | нет |
| Просмотр отчёта по заведению | да | нет | нет | да |
| Блокировка мерчанта | нет | нет | нет | да |
| Изменение справочников | да (свои сотрудники) | нет | нет | да |



\## Процесс регистрации мерчанта 



| Шаг | Кто делает | Что происходит | Проверки |
|—|—|—|—|
| 1 | Мерчант | Подаёт заявку: название заведения, описание, контакты | Название заполнено, 1–100 символов; описание не длиннее 200 символов; такого названия ещё нет в системе |
| 2 | Система | Создаёт запись мерчанта с новым merchant_id (формат m_NNN) и статусом PENDING, ставит заявку в очередь на проверку | merchant_id уникален; статус при создании всегда PENDING, задать другой нельзя |
| 3 | Администратор | Проверяет данные заявки и принимает решение: ACTIVE (одобрить) или BLOCKED (отклонить) | Решение принимает только администратор; мерчант сам себя активировать не может |
| 4 | Система | Сохраняет новый статус, записывает событие в аудит, уведомляет мерчанта | Только при ACTIVE мерчант может добавлять сотрудников и генерировать QR; при BLOCKED или PENDING эти действия запрещены (код ошибки MERCHANT_BLOCKED) |


\## Процесс регистрации сотрудника 



| Шаг | Кто делает | Что происходит | Проверки |
|—|—|—|—|
| 1 | Мерчант | Приглашает официанта: вводит его имя, система создаёт одноразовую ссылку-приглашение | Мерчант в статусе ACTIVE; приглашение действует ограниченное время и одноразовое |
| 2 | Официант | Переходит по ссылке, подтверждает имя и вводит реквизиты для выплат (карта или счёт) | Приглашение действительно и ещё не использовано; имя заполнено; реквизиты имеют корректный формат |
| 3 | Система | Создаёт employee_id (формат e_NNN), привязывает официанта к merchant_id из приглашения, сохраняет только маску реквизитов (****NNNN, последние 4 цифры) | Полный номер не сохраняется и не попадает в логи; один официант привязан к одному мерчанту; маска имеет вид ****NNNN |
| 4 | Система | Помечает приглашение использованным, записывает событие в аудит, уведомляет мерчанта | Повторно использовать приглашение нельзя |



\## Критерий приёмки

\- \[ ] Все 4 роли описаны

\- \[ ] Матрица прав заполнена (8 действий × 4 роли)

\- \[ ] Регистрация мерчанта: 4 шага с проверками

\- \[ ] Регистрация сотрудника: 3–4 шага

\- \[ ] Реквизиты сотрудника маскируются (\*\*\*\*1234), не хранятся открыто

\- \[ ] Клиент может сканировать QR только своего чека (привязка к receipt\_id)



\## Подсказки

\- Мерчант не может сам себя активировать — нужен администратор.

\- Официант не может видеть чаевые коллег — только свои.

\- Клиент анонимен (или имеет минимальный профиль), но нужен для антифрода.

\- Реквизиты (карта/счёт) — только для выплат, не для оплаты клиентом.
